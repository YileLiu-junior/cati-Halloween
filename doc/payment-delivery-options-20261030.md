# PETI 支付后交付与退款：现状核对及三个方案

日期：2026-10-30，北京时间。本文用于选择方案，尚未修改或部署支付、生图和退款功能。

## 1. 直接结论

1. 用户描述的回流摩擦属实：当前付款链接在原标签页打开爱发电，没有已验证的支付成功自动回跳。
2. “必须复制平台单号才生图”并非唯一设计路径。代码已有 Webhook 自动确认付款，手填单号是备用入口。
3. 现有 Webhook 只解锁订单。用户返回 PETI 后，页面才发起生图请求。这是需要改变的责任划分。
4. 爱发电官方支持自定义订单号 `custom_order_id`，支付 URL 可携带，Webhook 与查单响应可回传。
5. 因此，正常路径可以取消复制单号。服务器核实支付后即可自动提交生成任务。
6. 当前售卖商品 `product_type=1` 对该参数的保留情况，仍需真实订单验证。官方未单独列出该商品类型的兼容保证。
7. 推荐近期采用方案二：自动验单、后台生成，再通过爱发电私信送达专属订单入口。方案一是它的交付基础。
8. 本次线上未交付还涉及生成故障。改善回流不能代替排查该故障。

## 2. 现状：代码实际怎样运行

```text
选择角色、上传照片
  → PETI 创建订单并保存照片关联、角色、价格和用户凭证
  → 支付 URL 的 remark 写入 PETI 订单 UUID
  → 用户在原标签页进入爱发电并付款
  → 爱发电 Webhook 通知 PETI
  → PETI 用平台订单号再次查单
  → 校验金额、商品、型号、数量、留言
  → 订单状态改为 unlocked（已确认付款）
  → 等用户回到 PETI
  → 页面读到 unlocked，调用 POST /api/jobs
  → 服务端读取照片、参考图和固定 Prompt
  → Seedream 生成角色
  → Seedream 图层拆分并合成透明 PNG
  → 私有存储保存成品，订单改为 ready
  → 页面鉴权读取并显示图片
```

核心证据：

- `app/functions/api/checkout.js:14` 创建网站订单；`:21` 把订单 ID 写入 `remark`。
- `app/functions/api/afdian/webhook.js:18` 用留言找订单，再调用确认付款逻辑。
- `app/functions/lib/payment.js:30` 校验支付；`:47` 只改为 `unlocked`。
- `app/public/js/custom.js:163` 页面见到 `unlocked` 才开始生成。
- `app/functions/api/jobs.js:17` 同步等待生成；当前没有持久任务队列。
- `app/public/result.html:123` 付款链接没有新标签页目标。

当前页面每 5 秒查询本站数据库。这个轮询不会扫描爱发电订单。Webhook 没来时，普通“查询状态”无法发现付款，必须走备用确认入口。

当前匹配依赖可编辑的 `remark`。用户或平台改变留言时，自动匹配会失败。即使手填平台单号，后端仍要求留言等于网站订单 UUID，无法单靠单号补救。

只读查询了已配置线上 D1 数据库的最近 10 笔订单。实际返回 5 笔，其中最近一笔已关联平台付款：

| 项目 | 查询结果 |
|---|---|
| 创建时间 | 2026-10-30 12:44:02 |
| 开始生成 | 2026-10-30 12:47:58 |
| 已关联爱发电交易 | 是 |
| 生成尝试次数 | 1 |
| 当前状态 | `uncertain` |
| 错误码 | `GENERATION_UNCERTAIN` |
| 当前允许重试 | 否 |

这证明最近一笔已付款订单到达过生成阶段。它不能证明失败原因，也不能仅凭时间确认就是用户所说的那笔。

这个错误码覆盖多种情况：请求超时、网络中断、响应或 PNG 解析失败，以及生成超过 400 秒后查询时被改为未知。现有持久记录不足以区分这些情况。需要补充供应商 request ID、阶段耗时、HTTP 状态和运行错误记录。

当前交付包含两次串行模型调用，各有 180 秒上限。浏览器等待 390 秒。400 秒后仍生成中的订单，只在下次查询时改成未知，没有后台主动补偿。

部署文档记录过 Workers Free 的 CPU 配额风险。官方当前文档列出 Free HTTP 请求 CPU 时间为 10ms，等待外部 API 不计入 CPU 时间。PNG 解码、合成才会消耗 CPU。当前套餐和运行日志尚未复核，因此不能把该风险认定为本次根因。[Cloudflare 官方限制](https://developers.cloudflare.com/workers/platform/limits/)

## 4. 爱发电已证实的能力与边界

| 能力 | 结论 |
|---|---|
| URL 自定义订单号 | 官方列出 `custom_order_id` |
| 通知与查单回传 | 完整 API 文档的两个响应示例均包含该字段 |
| 平台交易号 | `out_trade_no`，由爱发电生成；不能与网站订单号混为一谈 |
| 主动查单 | 文档列出分页、平台订单号等参数；没有记录按 `custom_order_id` 直接筛选 |
| 支付后自动回跳 | 未找到公开官方支持；不等于已证明平台绝不支持 |
| OAuth2 回跳 | 属于授权完成后的返回，不是付款完成后的返回 |
| 主动私信 | 官方有 `send-msg`，支持收件人和正文；外链展示与点击效果需真机验收 |
| 单笔个性化自动回复 | 未找到模板变量支持；更新方案回复是全局操作，不适合逐单改链接 |
| 普通商品退款 API | 本次未找到公开官方接口 |
| 后台退款实际入口 | 本次未验证，不能假设已有按钮 |

依据：[官方功能汇总](https://afdian.com/p/010ff078177211eca44f52540025c377)、[官方完整 API 文档](https://afdian.com/p/9c65d9cc617011ed81c352540025c377)、[开发者指南](https://guide.afdian.com/creator/developer)、[OAuth2 指南](https://guide.afdian.com/creator/oauth2)。

官方提醒 Webhook 可能延迟，也可能重复推送。必须加入主动对账与去重，不能只依赖一次通知。[开发者指南](https://guide.afdian.com/creator/developer)

订单关联解决的是“这笔钱属于哪个 PETI 订单”。它不能证明两个页面的操作者是同一个自然人。交付不需要强制建立自然人身份，但必须保留独立的订单访问凭证。金额、时间、IP 或昵称都不能作为唯一认单依据。

## 5. 三个可选方案

### 方案一：保留爱发电，自动验单并后台生成

用户路径：上传 → 点击支付 → 爱发电付款 → 切回原 PETI 订单页 → 自动看到进度和图片。

1. 支付前创建唯一网站订单及随机关联码。
2. 在支付 URL 携带 `custom_order_id`。
3. 收到通知后，服务端查单，使用查单响应中的关联码匹配网站订单。
4. 核实交易后自动入队，用户不回页面也开始生成。
5. 桌面端保留原 PETI 页，并在新标签页付款。
6. 手机端按实际浏览器行为保留订单入口，用户切回时立即刷新状态。
7. 同一浏览器再次打开 PETI 时，显示“继续查看上次订单”。

优点：取消复制单号；无需新增登录；改动范围最小。

不足：爱发电没有已验证的支付回跳，手机用户仍可能手动切回。换设备或清除浏览器数据后，单靠本地保存无法找回。

退款搭配：订单页直接申请，自动附带付款记录；后台人工审核；通过已验证的爱发电实际渠道执行退款。

### 方案二：在爱发电内主动送达订单入口（近期推荐）

用户路径：上传 → 爱发电付款 → 收到“查看生成进度”私信 → 点击直达自己的 PETI 订单 → 完成后再收到提醒。

方案二包含方案一的完整底层机制，再增加：

1. 验单成功后，向这笔交易的爱发电付款账号发送专属订单入口。
2. 图片完成后，发送一次完成提醒。
3. 生成失败或超时后，在同一订单入口显示退款申请。
4. 退款申请与审核进度可沿同一通知渠道送达。
5. 私信发送失败时记录重试，生成任务继续执行。

专属链接必须带独立、随机、可撤销的访问凭证，且只授权该订单成品和售后。不能只有公开订单号，不能暴露原始照片或其他订单。付款前说明结果入口会发送至付款账号，代付用户也能理解收图位置。

站内固定自动回复可作为导航补充。不能每来一笔订单就修改全局回复，否则并发下可能发错链接。

优点：用户在爱发电内就能找到明确的返回入口；关页和跨设备恢复更容易；不要求新增 PETI 账号。

不足：仍有爱发电登录及付款界面；私信链接能否点击、是否有通知、打开哪个浏览器，都需实际设备验证。后台可以自动生成，不代表浏览器一定自动回跳。

退款搭配：私信中的订单入口同时承载申请和查询；审核与方案一共用；资金实际退回渠道仍需核实。

### 方案三：接入正式商户支付

用户路径：上传 → 微信等商户收银台 → 返回 PETI 指定订单页 → 查看进度和图片。

以微信支付为已核实例子：H5 支付支持 `redirect_url`；下单支持商户订单号和支付通知；退款有申请、查询与通知接口。回到页面后仍须验单，回跳本身不是付款凭证。[H5 开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791831)、[H5 下单](https://pay.wechatpay.cn/doc/v3/merchant/4012791834)、[退款申请](https://pay.wechatpay.cn/doc/v3/merchant/4013070371)

微信外 H5、微信内页面与桌面收款需要选择对应产品，不能用一个 H5 链接覆盖所有环境。商户号、应用绑定、开通权限和支付域名需按实际主体核验。若新增支付宝，另行核实对应产品的商户条件和接口。

优点：支付返回、商户对账和退款接口最完整；移除爱发电中间界面。

不足：接入和运营工作最大，存在资质及产品权限前置条件；不适合作为本次故障的唯一即时修复。

退款搭配：同一申请与审核系统，批准后调用渠道退款接口；收到成功通知或查询确认后，才标记已退款。

### 比较

| 维度 | 方案一 | 方案二 | 方案三 |
|---|---|---|---|
| 正常流程复制单号 | 不需要 | 不需要 | 不需要 |
| 用户离开后后台生成 | 支持 | 支持 | 支持 |
| 支付后找回 PETI | 切回原页 | 爱发电专属私信入口 | 对应支付产品的返回流程 |
| 跨设备找回 | 需额外恢复方式 | 可由付款账号私信进入 | 需站内订单恢复方式 |
| 新增 PETI 登录 | 无需 | 无需 | 依实际订单与支付方案 |
| 退款资金执行 | 先核实爱发电渠道 | 同方案一 | 已开通支付渠道 API |
| 相对实施量 | 小 | 中 | 大，且有外部开通条件 |

## 6. 三个方案共用的后台交付机制

以下为建议架构，尚未实现：

1. 支付前保存不可变订单快照：照片引用、角色、价格、生图配置版本和 Prompt 版本。
2. 持久保存收到的通知，再确认已收件；通知内的关联码只作线索。
3. 后台用创作者凭证查单，校验权威响应中的付款状态、金额、商品、型号、数量及关联码。
4. 原子记录已付款状态和待生成任务，防止“已付款写成功、任务未发出”。
5. 使用持久队列或工作流消费任务，定时扫描漏发任务并补投。
6. 生成与透明处理分阶段记录，保存源图、成品及各阶段请求标识。
7. 前端只查询和展示，不能承担启动已付款订单的必要职责。

不要仅把生图移进 Webhook 或 `waitUntil()`。Cloudflare 文档明确，HTTP 返回或断连后的 `waitUntil()` 延长时间最多 30 秒，不适合这个分钟级链路。[Cloudflare 官方说明](https://developers.cloudflare.com/workers/runtime-apis/context/)

队列可能重复交付。数据库要以订单和阶段做认领、去重及执行租约。供应商调用受理结果未知时，不能假设重试不会再次收费；若供应商没有可用查任务或幂等能力，应保留人工核对。[Cloudflare 队列交付保证](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)

付款对账采用后台统一调度与退避，不为每个浏览器分别拉取平台列表。官方未记录直接按自定义订单号查询，所以补偿扫描要覆盖分页和较早创建、较晚付款的订单。当前“全站 15 秒只准一次查单”的闸门应改为可排队处理，不能把同时到达的付款通知直接丢下。

建议将付款、交付、退款分开保存。一个网站订单可记录多笔真实支付，但只生成一份权益。第二笔付款进入退款处理。价格变化、照片到期、未知关联码和晚到付款进入异常台账，不静默丢弃。

## 7. 退款申请与审核流程

### 时间规则：建议值，待用户选择后确定

这些时间不是爱发电规则，也不是已验证的性能承诺。用户的退款资格按实际付款时间计算；平台能返回可靠的付款成功时间时，自动使用该时间。若无法取得该时间，内部生图告警从本站确认到账开始计时，但用户仍可先提交“已付款未识别”售后，人工按付款记录核实。通知迟到不能让用户重新等待完整退款时限。另存通知接收和验单时间，用于定位系统延迟。

| 条件 | 用户看到什么 | 后台动作 |
|---|---|---|
| 用户称已付，60 秒仍未确认 | “核对付款” | 发起服务端对账；不要求重新付款 |
| 明确不可恢复的生成失败 | 立即出现“申请全额退款” | 记录失败证据和退款资格 |
| 付款后 5 分钟未交付 | 延迟状态、等待时间、售后入口 | 检查付款核对、队列、执行租约、供应商和存储 |
| 付款后 10 分钟未交付 | 开放“申请全额退款”；付款尚未核实也可先受理 | 自动进入异常处理清单；用户离开也记录；退钱前核实付款 |
| 重复付款 | 多付款项处理入口 | 保留交易明细，建议全额退多付部分 |
| 已交付但质量不符 | “反馈图片问题 / 申请审核” | 人工核对原图、成品及说明，不用低评分作为唯一门槛 |

不能把“未知”写成“正在生成”，也不能让未知订单永远等待。达到退款时间即可受理申请，退款前再核对付款与交付事实。

用户申请：

1. 从订单页点击“申请退款”。
2. 选择未交付、生成失败、重复付款或图片问题。
3. 核对自动带入的金额；已有通知方式则带入，没有则可选补充，不作为申请门槛。
4. 提交后，在原订单页查看处理进度。

技术失败自动带错误记录，不要求评分或截图。正常已匹配订单无需填写任何订单号。只有无法关联的异常付款，才请求补充平台单号或凭证。

后台审核：

1. 打开带支付记录、生成阶段和退款原因的申请。
2. 核实资金是否到账、是否已退款、是否交付及是否重复付款。
3. 执行“批准”“驳回并说明理由”或“请求补充信息”。
4. 批准后通过已核实的渠道执行退款。
5. 收到退款成功证据后更新为“已退款”。

建议采用 24 小时内完成首次审核的服务目标。它不是资金到账承诺。图片问题应提供理由和一次复核路径。

退款状态：

```text
待审核 → 已批准 → 退款处理中 → 已退款
   ├→ 待补充信息 → 待审核
   └→ 已驳回 → 复核
退款处理中 → 执行失败 → 待重试或人工处理
```

申请提交后暂停新增生成和自动重试。已经送到供应商的调用可能无法取消。退款待审核期间晚到的图片先保留，不能自动撤销用户申请；若申请前尚未交付且已满足超时退款条件，不能仅因晚到图片而拒绝。退款批准或完成后，晚到图片不能恢复交付或取消退款。

每个申请和资金操作都要有唯一标识。退款接口超时后先查原退款单，不换新编号盲目重退。重复通知和点击不能重复扣款、重复退款或重启生图。

图片保留期与财务、售后记录分开。需要生成或交付补偿的订单先避免素材失效；成品的领取期限从交付时明确告知，不把大部分时间消耗在等待故障上。财务状态不能随图片清理一起消失。

### 爱发电资金退款的待验证项

方案一和二可以实现完整申请与审核，但尚未确认平台实际退钱的路径。应核实普通售卖商品的后台操作或官方人工渠道，并用真实测试订单走完一次。

如果平台不支持所需退款，必须另定可实际执行的退款方式，或切换支付渠道。任何线下退款都需要核实收款人并保存凭证，不能在尚未完成时标记“已退款”。本轮不代用户执行资金操作。

## 8. 实施前验证与交付验收

1. 用当前售卖商品实付，验证 `custom_order_id` 从 URL 经支付到 Webhook、查单完整保留。
2. 验证修改留言不影响新关联码匹配，并保留旧 `remark` 订单兼容核对。
3. 支付后关闭 PETI，确认后台仍开始且完成生成。
4. 重复推送同一支付通知，确认一份权益、一次阶段调用。
5. 模拟漏通知，确认定时对账能够发现付款。
6. 模拟任务写入或队列发送失败，确认待生成任务能够补投。
7. 模拟供应商结果未知，确认不会盲目重发收费调用。
8. 验证手机从爱发电私信返回、跨浏览器进入订单和通知失败降级。
9. 验证明确失败及超时退款入口、24 小时审核记录和完整退款实操。
10. 模拟退款与晚到图片同时发生，确认不会退款后重启交付。
11. 检查当前运行资源，并对生图、PNG 解码和透明合成分别记录实际耗时与错误。

本轮执行现有 API 测试：20 项中 19 项通过。素材配置一致性测试报 `Array buffer allocation failed`；尚无证据与线上未交付存在因果关系。支付验证、通知解锁、平台交易唯一约束、并发认领与未知结果禁重跑相关用例通过。本轮没有再次付费生成，没有退款，没有修改业务代码或生产状态。

## 9. 建议选择

选择方案二。先完成方案一的自动交付基础，再加爱发电专属私信入口和完成提醒。它直接减少当前复制单号和找回网页的摩擦，且无需新增 PETI 注册步骤。

同时将生成故障定位、持久任务执行、退款实操列为同一批交付内容。不能只优化付款按钮就认定支付后交付问题已经解决。若爱发电售卖商品关联码或真实退款路径验证失败，再调整为方案三或其他已验通渠道。
