## 三、质询发现

**G1｜§10.3 vs §1 上线门槛｜webview 回流排了期，却不在门槛里。** §10.3 排 10-28 验「小红书 webview 真机回流」，但 §1 门槛四项没有它——回流失败照样收费上线。回流失败时唯一兜底是「跳出前复制的凭证」，而凭证在 webview 里能否复制、能否恢复，同样只有真机验证能回答；兜底和主路径是同一次验证。后果：全部流量来源容器（小红书）的支付回路是唯一没被门槛保护的关键路径。**MODIFY**：回流列入门槛第五项。

**G2｜§5.5.2 + §1 门槛④｜§5.5「可用」依赖的供应商查询能力无出处、无排期。** 门槛④允许以「§5.5 中断补偿可用」替代 Queue，§12.1 缺省恰是不启用 Queue。但 §5.5.2「凭 attemptId 向供应商核查任务真实状态」假设火山方舟可按 attemptId 查任务并区分「从未受理」；technical-notes §8 只提推理用量查询 API，非任务状态；全文无任何核实记录。若 Seedream 是同步出图接口，「从未受理」与「受理且完成但响应丢失」不可区分，回滚永不触发。后果：K1 在缺省路径上重新打开，且 10-28 排期没有验证④的时刻。**MODIFY**：任务查询能力列入 10-28 验通项；不可用则 §12.1 缺省改为必须启用 Queue。

**G3｜§12.5 + §1/§7 整章｜退款实操未入门槛，§12.5 无缺省，悬空条款。** 门槛①只验「订单核验」，不验「爱发电能否实际退款」（technical-notes §9 明说须账户核实）。若平台不支持退款或手续费全损：退款中→已退款不可达，付费墙文案承诺「不像可申请退款」（interaction-design §2.1）成为无法兑现的消费者承诺，集中在评分环节爆发。且 §12 序言「到期未裁按缺省执行」对第 5 条失效——事实无缺省可落。**MODIFY**：退款实操真单一笔列入门槛①；§12.5 补缺省（未核实则付费墙文案删退款承诺）。

**G4｜§2.1、§3.4.3｜早鸟切换没有平台侧动作定义。** 截止后服务端 amountFen 判 590，但爱发电商品是平台侧固定价；PRD 无任何一条写「10-31 00:00 谁把爱发电商品改成 5.9 或下架早鸟 SKU」。值守窗口 19–22 点，截止点之后无人在线。后果：00:00 至人工改价之间，用户按平台价 2 元付款、服务端按 5.9 核验失败，全部标异常转人工退款——金额越小的单越没人理性处理，且全堆在次日 10:00 通道开启时。**MODIFY**：§2 或 §10.3 补运营动作（定时改价/双 SKU/专人 00:00 切换，任选其一写死）。

**G5｜§3.3.3、§9.3.2、§5.3.5、§9.2（jobs）｜原子性规格建立在 KV 不具备的原语上。** 三处「条件写/put-if-absent/原子扣减」全部落在 KV：认领 claim:{platformOrderNo}、jobs 的 已解锁→已使用、第二轮额度。Cloudflare KV 无条件写、最终一致（上游两文档自引官方说明）；上游设计原是「原子凭证存 R2」（interaction-design §1 K、technical-notes §1），v1.2 §9.3.4 的 R2 键里凭证消失了。MVP 已用先查后写绕过（PROJECT-STATUS §4.5 自认），quiz 单写路径够用，但认领和双设备并发提交是真正的多写者场景。后果：一份平台订单解锁两份权益、或双端并发双扣次，直接算错钱。**MODIFY**：认领与状态迁移改 R2 条件写或等价原子原语，§9.3 补 R2 凭证键。

**G6｜§3.6.2 + §9.2 + PRD-quiz §7.7｜恢复链接回不到订单。** 承诺「凭恢复链接恢复原结果与订单状态」，但 governing 接口 PRD-quiz §7.7 /api/recover 出参只有原结果（app/functions/api/recover.js 现实现同样无 payId/订单字段）；payId 只存旧浏览器 localStorage；§9.2 清单没有任何按口令返回 payId/订单状态的接口。上游 technical-notes §4 的 recover 本写明出参含「订单状态」，是 PRD-quiz 收窄后没接上。后果：换浏览器后用户看得见结果、看不见订单，已付的钱悬空走人工。**MODIFY**：/api/recover 出参补 payId 与订单状态，或在 §9.2 增补接口。

**G7｜§9.2（jobs）+ §5.5.2｜回滚后二次提交被旧 job 卡死。** 回滚置 job=failed-unstarted 并返还资格，但「同 payId 已有 job 返回原 jobId」无状态条件——重新提交只会拿回那个失败 job，没有新建路径。B6 即此。另：jobs 入参校验「照片审核通过且未过期」未含「照片属于本 testId」，存在跨会话引用 photoId 的校验缺口。**MODIFY**：「返回原 jobId」限定进行中状态（accepted/generating）；补照片归属校验。

**G8｜§9.2（photos）+ §4.5｜换图删旧 photoId 无状态门禁。** POST /api/photos「换图新 photoId、旧 photoId 即删」不限订单状态：job 已受理后用户换图，正在跑或待重绘的任务（§5.3.7 只重做对应步骤）引用的 R2 对象被当场删除。后果：用户一次无害换图把已扣次订单打成技术失败，甚至滑向退款。**MODIFY**：换图删除限定于订单已解锁且无进行中 job；受理后上传通道拒绝（PHOTO_INVALID）或静默忽略。

**G9｜§9.3.6｜「百单」测算漏了 quiz 共用写额。** 8–12 写/单 × 100 单 ≈ 1000 = 免费档全日额，同一账户下 quiz 每用户 ≥2 写（PRD-quiz §7.6 自称「数百日活即触顶」）未计入。灰度日 quiz 流量与付费单并存时，写额先于付费峰值触顶。10-30 前置决策能看到真实量，但 PRD 给的口径本身失真，照抄会误判余量。**MODIFY**：改为 quiz+订单合并测算。

**G10｜§3.3.4、§9.2（checkout）｜「未完成 payId」未定义，同结果第二单无入口。** 订单状态机没有「已交付」终态，已使用是否算「未完成」未定义。若算：用户想给同一结果买第二张（换张照片）永远被指回旧单——「每单 1 张」的商业设计没有第二次购买入口；若不算：§3.3.4 的约束名存实亡。**OPEN**：作者定义未完成集合（建议 unpaid/verifying/unlocked），并裁决同 testId 二次购买是否支持。

**G11｜§3.1.3、§3.3.1｜留言降级路径的自动化归属悬空。** custom_order_id 不可透传时降级「复制 payId 填订单留言」，但留言能否被 API 读回用于自动认领从未验通。若不可读回：自动核验全灭、批量转人工，而 §1 人工通道定义的是身份核验与退款的响应时段，不是批量认单流程。**OPEN**：10-28 验通①时一并回答「留言字段 API 可读吗」，并写明不可读时的认单流程归属。

**G12｜§6.6、§6.10｜宠物名 UGC 无过滤直接进传播面。** 宠物名经 canvas 上卡、进分享文案、进文件名（仅滤路径字符），随小红书二次传播；敏感词、辱骂性名称无任何拦截。5 天活动实际风险低，但成本也低（一份屏蔽词或限字符类型）。**OPEN**（低危）：作者裁决是否值一小时工作量。

**G13｜§3.6.2｜恢复链接即生成权凭证，无失效与轮换机制。** 转发链接给朋友看图=朋友可消耗这次生成、可提交退款申请；无「重置口令」操作，「建议复制保存」与「分享文案」在 UI 上是两个东西，用户混发概率不低。**OPEN**（低危）：作者明示接受即可，加一句文案区分二者。

扫过不立案：23:59:59 边界（§3.4.4 平台真实字段已覆盖）、多设备并发（并入 G5）、免费用户付费墙（§3.1.1 门禁+上游弹层规格齐全）、狗版 prompt（门槛③样图已盖）、五色缺省（四色+近黑派生自洽）、微信长按保存元信息（上游矩阵兜底）。

## 四、KEEP（站得住的部分）

§5.4 终态+§11.6 回滚验收、§10.2 指标四件套（窗口/核验/分层/双率）、§12 缺省裁决机制框架、§1 人工通道条目、§6.10 分享收编与编号漂移记录、§4.6 残留风险明示。修订整体是认真的，问题集中在「验证清单与门槛没对齐」和「原子性/接口两处实现层断裂」。

## 五、最强反面论证

v1.2 关闭了第一轮的「条款缺失」，没有关闭第一轮的「未验证依赖」，并且修订自身制造了三处新的纸面闭环：门槛清单看着变硬（四项），实际最日常致命的回流断链不在清单里；§5.5 的回滚机制写得很完整，但它假设的供应商查询能力无出处、无验证排期，缺省路径（不启用 Queue）恰好整条押在它上面；售后承诺（退款）的执行机制既不在门槛也无缺省。再加上原子性全部写在 KV 这个不提供该原语的存储上——10-28 验通日若按 §10.3 清单走完，会出现「门槛全绿、上线当天仍然翻车」的窗口：回流断链让首批付款全转人工，认领竞态在峰值并发下现形，退款承诺无法执行。工程严谨度高，但严谨的条款盖在未验证的地基上。

失效条件：若 10-28 验通清单扩为「门槛四项 + webview 回流 + 退款实操 + 供应商任务查询 + 双并发认领实测」，且 G5 改 R2 条件写，则本论证失效，方案按期成立。

## 六、Premortem（死因 ≤3）

1. **验通日全绿、带病上线**：webview 回流与退款实操不在门槛，首批付款用户回流断链全转人工，单人通道在 10:00 前堵死，差评集中爆发。
2. **峰值夜原子性竞态现形**：KV 先查后写挡不住并发认领与双端提交，一份订单两份权益或双扣次；修的是实现，背锅的是规格（§9.3 写错了存储）。
3. **截止时刻商品价未切**：00:00 后 2 元付款批量标异常，次日 10:00 通道开启时退款请求堆积，24 小时核实承诺当天击穿。
